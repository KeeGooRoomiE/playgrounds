# Architecture

## Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Astro 5, `output: 'static'` | No SSR needed — the whole site prerenders to `dist/` and ships to GitHub Pages |
| Content | Markdown + frontmatter, Content Layer API (`src/content.config.ts`, `glob()` loader) | Body markdown carries the algorithm write-up, frontmatter drives cards/filter/OG — one file is the source of truth per playground |
| Islands | Per-playground `.astro` component under `src/islands/`, rendered plainly — **no `client:*` directive** | Each playground is a self-contained canvas + script. `client:*` applies only to framework components (React/Vue/…); a plain `.astro` island's `<script>` is a normal ES module that runs at page load. Isolation comes from slug-prefixed DOM ids and module scope, not from hydration |
| Styles | Plain CSS custom properties (`src/styles/global.css`), one light theme | No theme switcher needed. Tokens are derived from the project's own `TEMPLATE.html` (the flat `#f5f5f5` / `#0066cc` look every standalone playground already used), not from the sibling `cv_hub` |
| Fonts | IBM Plex Sans (variable) + IBM Plex Mono, self-hosted via `@fontsource` npm packages, imported in `Layout.astro` | Chosen over a system stack so the site renders identically everywhere, and over a CDN so there's no external request. Sans and mono are one family — the pages are half prose, half pseudocode. Stacks live in `--font-sans` / `--font-mono`; subsets split by `unicode-range`, so an English page fetches one ~45 KB file |
| Backgrounds | Swappable `.astro` components under `src/components/backgrounds/`, `DefaultBackground` fallback | A playground can opt into its own themed background later without touching `Layout` |
| Deploy | GitHub Actions → `actions/deploy-pages` | `site`/`base` resolve from `GITHUB_REPOSITORY` at build time, so the repo can be renamed/forked without editing config |

## Folder structure

```
playgrounds/
├── src/
│   ├── content.config.ts             # `playgrounds` collection schema (Content Layer API)
│   ├── content/playgrounds/          # one .md per playground (template lives at docs/PLAYGROUND_TEMPLATE.md, outside the collection)
│   ├── components/
│   │   ├── Layout.astro              # shared shell: head/OG, background slot, <slot>/<Footer> (no header)
│   │   ├── Footer.astro
│   │   ├── PlaygroundCard.astro
│   │   ├── CategoryNav.astro         # index rail: entries grouped by `category`, collapsible <details>
│   │   └── backgrounds/              # DefaultBackground.astro + opt-in extras (PlayStationWaves, ...), index.ts registry
│   ├── islands/                      # one self-contained .astro per playground
│   ├── pages/
│   │   ├── index.astro               # category rail + tag filter + card grid
│   │   └── [slug].astro              # detail page — identical structure for every entry
│   └── styles/global.css
├── public/thumbnails/                # committed PNGs, generated by scripts/capture-thumbnail.mjs
├── scripts/                          # scaffold-playground.mjs, capture-thumbnail.mjs
├── docs/                             # internal reference docs, committed (see docs/CREATING_A_PLAYGROUND.md)
├── ARCHITECTURE.md                   # this file
└── .github/workflows/{deploy,thumbnails}.yml
```

## Data pipeline

```
source repo's index.html (prose + canvas + script)
        │  scripts/scaffold-playground.mjs <slug> <path-to-index.html>
        ▼
src/content/playgrounds/<slug>.md   +   src/islands/<PascalSlug>.astro
        │  manual review: id-namespacing, tags, order, description, thumbnail
        ▼
content.config.ts validates frontmatter
        │
        ├──► src/pages/index.astro                (260px category rail + tag filter + card grid)
        └──► src/pages/[slug].astro
                 ├─ render(entry) + <Content />      → prose body
                 └─ islands[entry.data.island]        → <Island />  (no client:* — see Stack)
```

## Routing

- `/` — list of every entry, sorted by `order` (ties broken by `title`).
- `/{slug}/` — one static route per collection entry via `getStaticPaths()`, e.g. `keegooroomie.github.io/playgrounds/boids/`. Every entry renders through the exact same page component — no per-playground page layouts, no sidebar, no prev/next — a single vertical column: back-link → title → full prose body → the island → source-repo note. The only navigation is the "← Back to all playgrounds" link above the title, plus a desktop-only floating back-to-top button that appears past 1280px of scroll. Category browsing lives on the index, not here.

## Backgrounds

`Layout.astro` accepts an optional `background` component prop. Each playground's frontmatter can carry an optional `background` key (same shape as `island` — a lookup key, not a path) resolved to a component by the detail page; if absent, `Layout` falls back to `DefaultBackground.astro`. The homepage always uses the default.

## CI/CD

Three workflows, each with a distinct trigger:

```
pull_request → main          ci.yml
  └─ npm ci → build with production base path → content integrity check

push → main                  ci.yml (same checks) + deploy.yml
  │
  ▼  deploy.yml
npm ci --omit=dev → npm run build → upload-pages-artifact → deploy-pages
  │
  └─ notify_telegram (optional; no-op without PIPLINE_BOT_SECRET/CHAT_ID)

workflow_dispatch            thumbnails.yml
  └─ full install → Playwright → capture → upload artifact (never auto-commits)
```

**`ci.yml`** is the gate for pull requests — `deploy.yml` only fires on push to
main, so without this a PR would look green while breaking the site on merge. It
uses `pull_request`, never `pull_request_target`: a fork's build script runs with
a read-only token and no access to secrets. Besides the build it runs a content
integrity check that the build itself can't catch — a `thumbnail` pointing at a
file that was never committed still builds fine, it just produces a page whose
`og:image` 404s, invisible until someone shares the link. It also verifies each
entry's `island` key is registered and its `category` appears in its own `tags`.

**`deploy.yml`** has no Playwright/Chrome step — thumbnails are static committed
files, not regenerated per build — and installs with `--omit=dev` for that
reason.

**`thumbnails.yml`** re-captures thumbnails in a clean room on demand: build →
preview server → Playwright screenshot → downloadable artifact (never
auto-committed; see `docs/CREATING_A_PLAYGROUND.md` for why). Capture is
deterministic: islands with randomness read `?seed=` (`src/lib/seed.ts`) and the
script always passes `?seed=kgrm_s121`. It blanks `GITHUB_REPOSITORY` for its
build and preview steps — the runner sets that variable automatically, which
would resolve `base` to `/<repo>` and make `astro preview` serve under that
prefix while the capture script requests root-level URLs.

### Workflow conventions

- **Every dynamic value goes through an `env:` block**, never `${{ }}` spliced
  directly into a `run:` script — expression interpolation happens before the
  shell parses anything, so an inline dispatch input is a command-injection
  vector, not a string.
- **Permissions are per-job, default-deny.** Each workflow starts
  `permissions: {}`; a job adds only what it needs (`contents: read` to build,
  `pages: write` + `id-token: write` only on the deploy job).
- **`persist-credentials: false` on every checkout.** `npm ci` executes
  dependency lifecycle scripts; there's no reason for a usable token to be
  sitting in `.git/config` while that happens. Nothing here pushes.
- **Action versions are kept current by Dependabot** (`.github/dependabot.yml`,
  monthly, grouped). Left alone they drift into runner deprecation warnings.

## Environment variables

| Var | Set where | Purpose |
|---|---|---|
| `GITHUB_REPOSITORY` | Automatically by GitHub Actions; export locally to test | Resolves `site`/`base` in `astro.config.mjs` — `GITHUB_REPOSITORY=owner/repo npx astro build` reproduces the production build locally |
| `PIPLINE_BOT_SECRET`, `CHAT_ID` | GitHub repo Settings → Secrets → Actions (not a local file) | Optional deploy-status notification to Telegram, mirrors `cv_hub`'s workflow |

See `.env.example` for the one local-only var.

## Key trade-offs

| Decision | Rationale |
|---|---|
| No CMS, no accounts, no progress tracking | Out of scope for this iteration — static content edited by hand |
| No search service (Pagefind/Algolia) | Client-side tag filter is enough at a few dozen entries |
| Single theme, no i18n | One author, one language, one look — no switcher infrastructure to maintain |
| Thumbnails are static, committed files | Avoids a Playwright/Chrome dependency in CI; regenerate manually via `npm run thumbnail -- <slug>` when a playground's visuals change |
| No single generic control-panel component across all islands | The 7 source playgrounds split into genuinely different control schemes (sliders vs. toggle+stats vs. preset buttons) — only the CSS is shared, not the markup/behavior |
